## Purpose

This workflow adds Peter and Peter-directed AI workers to the existing Elevation Operating System without creating a second control plane.

The design rule is:

**ONE REPOSITORY → ONE MASTER S.O.P. → ONE GLOBAL WORK BOARD → PETER READS GLOBAL STATE → PETER WRITES HIS OWN LANE → MATERIAL DELTAS ROUTE UP.**

The parent authority is the accepted OS 1.1 composite control set: `operations/MASTER_SOP_V1_0.md` + `operations/MASTER_SOP_V1_1.md` + accepted OS 1.1 modules. V1.0 remains the non-regression foundation.

## Authority boundary

Peter and Peter-directed AI workers may read the public repository to understand current company/project state.

Reading a control surface does not grant authority to rewrite it.

**READ GLOBAL ≠ OWN GLOBAL.**

Peter's Git lane is a delegated operating surface under Company Operations / current MPM oversight. It is not a competing Master Work Board and does not create another management hierarchy.

## Required startup

Peter-directed Git-aware work starts with:

**GIT FIRST → RESOLVE CURRENT `main` → READ MASTER S.O.P. V1.0 + V1.1 CONTROL SET → READ OS 1.1 EXECUTION/HANDOFF CONTROL → READ CURRENT WORK BOARD → READ PETER MANAGER INDEX → READ THE OWNING PROJECT/WORKTREE → VERIFY ASSIGNMENT → EXECUTE.**

### Hard preflight gate

No substantive analysis, recommendation, drafting, mutation, publication, send, upload, deployment, or project-state claim may occur before the Git-first check is complete for Git-aware work.

The worker must record a compact startup receipt before proceeding:

**GIT CHECK → current `main` SHA → control files read → owning Project/Worktree resolved → assignment confirmed.**

If the worker cannot resolve current Git:

**STOP ONLY THE GIT-DEPENDENT WORK → REPORT GIT CHECK FAILED → DO NOT SUBSTITUTE MEMORY OR OLD CHAT STATE.**

A stale chat summary, old handoff, historical MPM number, remembered product state, or prior local note is never a substitute for the Git-first check.

Do not use old chat prompts, historical MPM numbers, old handoffs or stale local notes as current authority when current Git is available and consistent.

## Protected global control surfaces

Peter's lane does **not** independently change the following merely because it can read them:

- `operations/MASTER_SOP_V1_0.md`
- global priority in `operations/CURRENT_WORK_BOARD.md`
- company-wide project ownership
- owner directives
- cross-project routing policy
- release/deployment authority
- another Project's controlling Worktree
- security, banking, credential or recovery controls

If a verified Peter-lane result materially changes global state, record:

**MASTER UPDATE REQUIRED**

with:

**VERIFIED CHANGE → SOURCE/EVIDENCE → AFFECTED PROJECT → PRIOR STATE → NEW STATE → RECOMMENDED GLOBAL UPDATE → TIMESTAMP.**

Company Operations / current MPM then reconciles the global control surface.

## Branch / commit discipline

Peter may use the same repository through his own authorized GitHub identity.

Preferred behavior for normal bounded Peter-lane documentation:

**FETCH CURRENT FILE → VERIFY SHA/STATE → EDIT ONLY ASSIGNED SCOPE → COMMIT CLEARLY → VERIFY RESULT.**

For broader or cross-project changes, use a focused branch/PR unless current management explicitly authorizes a direct write.

Do not share Casey's password, MFA, recovery credentials or owner session.

## AI worker rule

Peter's AI worker is an execution/support worker unless a separate current Git file explicitly assigns a management role.

It must:

- fit into the existing OS before creating structure;
- continue existing work before creating duplicates;
- use current Git instead of stale prompt memory;
- keep customer-facing content free of internal control language unless the assignment specifically calls for internal documentation;
- preserve one primary execution owner per task;
- stop only the blocked item and keep unrelated clean work moving;
- verify before claiming completion.

## Peter Manager Index role

`operations/peter/PETER_MANAGER_INDEX.md` is Peter's durable orientation and routing surface.

It may summarize Peter-owned current state and point to controlling company/project records.

It may not become a duplicate company-wide Work Board.

## Security and public-Git rule

Never write to public Git:

- passwords, access tokens, MFA/recovery codes or private keys;
- raw customer PII;
- protected supplier costs or private dealer sheets;
- private carrier rates when protected;
- confidential vendor correspondence;
- bank/payment credentials;
- security-recovery details.

Use public-safe status, references, manifests and receipts only.

## Control statement

**READ GLOBAL → WRITE LOCAL → ROUTE MATERIAL CHANGE UP → DO NOT DUPLICATE CONTROL → VERIFY BEFORE CLAIM → KEEP THE OS MOVING.**
