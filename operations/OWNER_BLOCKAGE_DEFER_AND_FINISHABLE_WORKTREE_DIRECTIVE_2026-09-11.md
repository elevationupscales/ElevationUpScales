# Elevation UpScales — Owner Blockage-Deferral / Finishable-Worktree Directive

**Status:** ACTIVE / OWNER DIRECTIVE
**Effective:** 2026-09-11
**Owner:** Casey Young
**Applies To:** Operating System Project Manager, Company Operations Manager, dedicated Project Operations Managers, Project Specialists, and assigned workers operating under `RUN` / `CONTINUE WORKFLOW`

## Owner direction

When an active workflow reaches a real blockage that cannot be cleared immediately with the available authority, access, tools, or verified source data, **do not let that blocked item hold the front of the workflow**.

Move the blocked item to the end of the applicable project/workflow queue with its exact blocker/trigger preserved, then continue every independent worktree that can still be completed.

## Required execution order

**GIT FIRST → RESUME CURRENT WORKTREE → EXECUTE UNTIL REAL BLOCKAGE OR COMPLETE → RECORD BLOCKER/TRIGGER → DEFER BLOCKED ITEM TO END → CONTINUE NEXT EXECUTABLE WORKTREE → REPEAT → RETURN TO DEFERRED ITEMS AFTER FINISHABLE WORK IS EXHAUSTED**

## What counts as a deferred blockage

Examples:
- waiting on supplier reply;
- waiting on customer reply;
- authenticated owner/admin access required and unavailable in the active tool/session;
- missing exact source data that cannot be safely inferred;
- external platform processing/review;
- owner approval genuinely required;
- technical tool/access limitation with no safe alternate route.

The blocked item remains OPEN. Deferral changes execution order; it does not close, cancel, erase, or downgrade the obligation.

## What does not qualify as a blockage

Do not stop or defer for:
- completed setup;
- optional enrichment;
- internal report formatting;
- stale historical notes;
- one worker/tool failure when another safe in-project route exists;
- another project's unrelated external wait;
- absence of a first order where catalog/source/preparation work can still continue.

## Project-lane control

Dedicated project managers remain inside their assigned project. They defer blocked sub-items to the end of that project's queue and continue other executable sub-items inside the same project.

The Operating System Project Manager / Company Operations Manager may continue across properly owned project rows after a blocked project/item has been durably recorded.

Workers do not self-transfer into another project. Out-of-lane work remains `ROUTE REQUIRED`.

## Blocked-item record

Every deferred blocked item must retain:
- WORK ITEM
- OWNER
- STATE
- BLOCKER
- TRIGGER TO RESUME
- NEXT ACTION ON RESUME
- CLOSE CONDITION
- SOURCE RECORD

## Return order

After all currently finishable worktrees have been completed or advanced to their next real gate, return to the deferred-blockage queue in priority order and recheck whether any trigger has cleared.

## Control phrase

**BLOCKED GOES TO THE BACK — FINISHABLE WORK MOVES FORWARD — NOTHING DISAPPEARS.**
