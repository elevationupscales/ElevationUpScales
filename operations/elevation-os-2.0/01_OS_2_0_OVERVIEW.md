# ELEVATION OS 2.0 — Peter Operating Overview

## What changed

Elevation's OS has matured from chat-heavy handoffs into a persistent Git-backed operating system.

The key change is not a new management hierarchy. It is a stronger recovery model:

**CHAT IS A WORKSPACE. GITHUB IS THE RECOVERABLE CONTROL SURFACE.**

A new worker should not rebuild company context from an old conversation. It should resolve the current repository state and fit into the existing Project.

## Company architecture

**CASEY — OWNER**  
↓  
**OPERATING SYSTEM PROJECT MANAGER / COMPANY OVERSIGHT ROLE**  
↓  
**COMPANY OPERATIONS + DEDICATED PROJECT MANAGERS**  
↓  
**SPECIALISTS / WORKERS / PLATFORM OPERATORS**  
↓  
**VERIFIED RESULT → STATE UPDATE → NEXT WORK**

Numbered MPM/COM/Recon chat names are continuity/session labels. They are not permanent independent authority layers.

## Core operating loop

**KNOW → RECONCILE → PRIORITIZE → ROUTE → VERIFY → UPDATE → CLOSE**

Execution rule:

**VERIFY → FIX IF POSSIBLE → COMPLETE IF CLEAN → HOLD ONLY THE BLOCKED ITEM → MOVE ON**

One blocked item should not stop unrelated executable work.

## Project first, worker second

A Project defines the operating home.

A worker receives a bounded role inside that Project.

Use:

**PROJECT FIRST → WORKER SECOND**

and:

**ONE MATERIAL TASK = ONE PRIMARY ACTIVE EXECUTION OWNER**

Shared workers may assist, but they do not create parallel ownership.

## The four OS layers

OS 1.1 separates:

### Policy
Durable rules and authority.

### Live State
What is true now.

Canonical company index:

`operations/CURRENT_WORK_BOARD.md`

### Scope / Worktree
Scope defines what may be worked.

Worktree defines what should be worked next.

### Evidence
Facts, receipts, platform results, correspondence and technical proof.

Evidence can correct facts but does not automatically create management authority.

**NEW FACT ≠ NEW AUTHORITY.**

## Master Work Board vs Project Worktree

The Master Work Board is the high-level company state and routing surface.

It should not contain every SKU, email or micro-task.

Detailed execution belongs in the owning Project's Scope / Worktree.

The worker should use the Work Board to understand company state, then enter the correct Project and continue from the existing Worktree.

## Continue before create

Before creating a new:

- Project;
- vendor effort;
- listing queue;
- email thread;
- research lane;
- freight inquiry;
- worker structure;

check current Git.

If the outcome already exists:

**CONTINUE THE EXISTING WORK.**

This prevents duplicate outreach, duplicate listing efforts, stale parallel worktrees and competing management queues.

## RECON

RECON is an integrity/reconciliation function.

It checks for:

- stale pointers;
- duplicate ownership;
- conflicting state;
- replay of completed work;
- wrong Worktree;
- release/SHA drift;
- lost open work.

RECON is not automatically another manager or execution owner.

## GIT FIRST

Git-aware work begins by resolving current `main` and reading the minimum relevant accepted control.

For a fresh Peter Project:

**CURRENT MAIN → MASTER V1.0 + V1.1 CONTROL → CURRENT WORK BOARD → PETER INDEX/WORKTREE → OWNING PROJECT → ASSIGNMENT**

Once a bounded task is validated, do not keep repeating broad recon.

Resolve once, work the task, verify, update, report.

## Peter's role

Peter is Ecommerce & Vendor Operations management / human execution capacity.

AI should absorb repetitive preparation:

**RECON → VERIFY → PREPARE → NORMALIZE → DRAFT → ORGANIZE**

Peter's human time should be used where it adds value:

- authenticated platform interaction;
- vendor/customer context;
- practical ecommerce judgment;
- final review;
- bounded human-only steps.

The system should not create a giant backlog for Peter.

## Peter's Git lane

Peter uses the same company repository.

His worker can read the public-safe global OS state needed to work correctly.

Normal write authority is Peter-owned state under:

`operations/peter/`

Use:

**READ GLOBAL → WRITE LOCAL → ROUTE MATERIAL CHANGE UP.**

This provides visibility without creating a second company control plane.

## Customer-facing work

Internal controls belong in internal state.

Customer-facing brochures, product listings, sales sheets and catalogs should sound like sales material.

Do not leak internal terms such as:

- internal gate;
- order-path control;
- worker queue;
- release candidate;
- verification state;
- pre-distribution;
- management hold;

unless an internal document was requested.

Use verified product facts, approved imagery, benefits, use cases and clear customer language.

## Owner gates

Routine authorized work should move without unnecessary owner interruption.

Protected actions still require the correct owner authority, including major financial/binding commitments, sensitive legal/tax actions, security/recovery actions, and external sends without established authority.

## Verify before claim

Do not claim:

**DONE / LIVE / SENT / PUBLISHED / DEPLOYED / PAID / SHIPPED / APPROVED / FIXED**

without verifying the relevant state.

Unknown external result:

**UNKNOWN → VERIFY BEFORE RETRY**

## Recovery rule

When a chat rolls over:

**DO NOT REBUILD THE OS FROM CHAT.**

Use:

**CURRENT GIT → CURRENT WORK BOARD → CURRENT LANE → CURRENT WORKTREE → NEXT ACTION**

That is the core of ELEVATION OS 2.0 for Peter.
